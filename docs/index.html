Regressa

Prompt evaluation and regression testing. Run a fixed set of prompts against an LLM, check the outputs against expected criteria, and flag regressions when prompts, models, or system instructions change.

See a real report Source

Prompt changes have no compiler and no type system. You tweak a system instruction to fix one behaviour, ship it, and silently break three others. Regressa gives that workflow a test suite, a baseline, and a diff. 

# No API key and no cost — the mock provider exercises the whole harness.
regressa run suites/offline-demo.yaml --set-baseline

# Change a prompt, then re-run. Exits 1 so CI catches it.
regressa run suites/offline-demo.yaml

A suite is one YAML file

targets:
  - id: v1-live                    # the prompt in production
    model: claude-sonnet-5
    system: |
      Refunds are available within 30 days of purchase.
      For security breaches, your reply must contain the exact
      phrase "escalating to a specialist".
      Three sentences maximum.

  - id: v2-candidate               # the rewrite you're considering
    model: claude-sonnet-5
    system: |
      Refunds within 30 days. For breaches, hand off to a
      specialist. Keep it short.

cases:
  - id: escalate-security-breach
    prompt: "Someone downloaded our entire client folder."
    assertions:
      - type: contains             # a contract, not a preference:
        value: "escalating to a specialist"   # ticket routing greps for it
        weight: 3
      - type: length
        unit: sentences
        max: 3

That rewrite is shorter, warmer, and cheaper to send. A reviewer would approve it. It also drops the literal phrase downstream ticket routing depends on, and swaps a hard sentence cap for "keep it short". Both break silently. 

regressa compare v1-live v2-candidate --fail-if-worse
verdictcasev1-livev2-candidatedetail
a_onlyescalate-security-breach PASSFAIL missing ['escalating to a specialist']
a_onlybrevity PASSFAIL 6 sentences > max 3
b_onlytone-under-pressure FAILPASS no filler apology

v2-candidate fails 2 case(s) that v1-live passes. Not safe to promote as-is — even though it genuinely improves tone.

Assertions

Deterministic

contains, regex, equals, json_schema, json_path, length (chars/words/lines/sentences), latency, cost, tokens. Free, fast, never flake — these carry the load.

Model-graded

llm_judge grades against a rubric using schema-constrained JSON, so the verdict is parsed rather than scraped from prose.

Semantic

similarity scores embedding cosine against a reference. Measures topic, not truth — a flat denial of your refund policy still scores 0.52 against it, so don't gate policy on it.

Design decisions worth knowing

A provider error is not a regression

Network failures are classified errored and kept out of the regression count. A gate that goes red on connectivity is a gate people learn to ignore.

A new failing case is not a regression either

It never passed, so nothing regressed. It shows up as added.

Targets are validated before a request is spent

temperature and top_p are rejected with a 400 on Opus 5, Sonnet 5, and Fable 5. A suite that sets them would fail every case for a reason unrelated to the prompt, so Regressa refuses the target up front and says which line to change. Same for thinking: disabled above effort: high.

Cost accounting is date-aware

Sonnet 5's introductory rate is modelled with an explicit end date rather than baked into the headline price, so costs reflect the rate actually in force. regressa models warns how many days remain — a promotion ending shifts every cost figure with no prompt change, which can trip a cost assertion overnight.

Flapping and jitter are different problems

regressa calibrate measures run-to-run variance from stored history and recommends a --tolerance. Cases that flip pass/fail are reported separately and excluded from the recommendation: no tolerance fixes flapping, and widening the gate to cover one would mask real regressions everywhere else.

Try it

git clone https://github.com/your-org/regressa
cd regressa
pip install -e .

regressa run suites/offline-demo.yaml --set-baseline
regressa run suites/offline-demo.yaml \
  --var greeting_reply="As an AI language model, I cannot assist."

No API key needed for any of that — the mock provider drives the entire harness, which is also how the 197-test suite runs.

Project status — honest version. The tooling is complete and tested offline: 197 tests, 88% coverage. The live Anthropic path is partially verified — credentials and request acceptance are confirmed against the real API, but response parsing, cost accounting, streaming, and the capability table have not yet been exercised by a successful call. Run regressa doctor with credit on the account to close that gap. Treat this as a working project, not a finished product.

Prior art

This space is not empty. promptfoo covers much the same ground — YAML suites, assertions, multi-provider, CI exit codes — at far greater maturity, and is what you should reach for in production. Regressa was built to work the problem from first principles; its distinctive pieces are the pre-flight capability validation, date-aware pricing, and the flapping/jitter split described above.
